Documented rationale means an explicit reason in an accepted ADR or requirement. Observed choice means code does it but a selection rationale was not found. Mentor analysis means an interpretation, alternative, or trade-off offered for learning; it is not a historical decision. Planned requirement describes behavior still to implement.

D1 · Persistent Product Profile and authenticated owner workflow

Problem: repository context, goals, inventory, operating constraints, and ownership must survive recurring work and ticket handoffs. Selected approach: one durable, credential-free per-product profile, completed incrementally through an authenticated workflow. Status: accepted ADR; implemented in SUC-6.

Documented rationale: ADR 0001 explicitly selects persistence over a one-request CLI to avoid rediscovering context across SUC-7/SUC-11. The server derives identity from verified authentication; readiness describes configuration.

Alternatives and trade-offs — mentor analysis: per-run CLI flags make small experiments easy but repeatedly carry configuration and identity. A static configuration file reduces setup UI work but needs an owner-safe update process. A persistent profile concentrates context, at the cost of storage, update rules, stale data handling, and access control. Limitations: current setup is HTTP JSON, not a rich owner dashboard; read-only status is not activation or approval.

Code: ProductProfile, registerProduct, updateProductProfile. Tickets: 6, 7, 11.

D2 · Persist candidates with original evidence and inventory verification

Problem: later demand evaluation must reuse an interpreted need and its evidence, rather than recreating transient groups every week. Selected approach: durable candidates keyed by underlying need, linked original feedback, comparison outcomes, and an owner-verified snapshot. Status: accepted ADR; branch implementation for SUC-7, which remains In Progress.

Documented rationale: ADR 0002 chooses persistence over a transient analysis response to enable reuse. It requires a current verification record, a trusted ticket-finder seam, and excludes bugs, fulfilled scope, existing tickets, and uncertainty from SUC-8's new proposals.

Alternatives and trade-offs — mentor analysis: recompute groups on every evaluation, or derive them from an immutable event history. Recomputing avoids a stale candidate cache but can change identities and duplicate proposals; an event log can preserve richer history but increases schema and replay complexity. Persisted snapshots simplify the handoff, while requiring explicit invalidation and reevaluation rules. Limitations: current “same need” comparison is exact text, snapshots contain reference strings rather than commit/content hashes, and no complete candidate-history GET exists.

Code: Candidate, InventoryVerification, analyzeFeedback. Tickets: 7, 8, 15.

D3 · Server-derived owner identity; feedback remains evidence

Problem: a submitted owner ID or customer message cannot authorize access or operations. Selected approach: bearer tokens map to owners server-side; every product operation checks ownership; accepted feedback preserves text without executing it. Credentials are excluded by validation. Status: implemented access checks, with future build authority still planned.

Documented rationale: ADR 0001 and SUC-5 explicitly require verified identity, product-scoped access, credential-free records, and untrusted feedback. Observed choice: environment JSON token mapping is the current authenticator. No rationale selecting it over another authentication system was recorded.

Alternatives and trade-offs — mentor analysis: an identity-provider session or signed token can support richer lifecycle management; a small opaque-token map is simple to inspect and test but has no implemented rotation UI, expiry, or separate roles. Regex credential rejection catches known patterns but is not a general secret-detection guarantee. Customer identity remains submitter-supplied attribution, so stable identity provisioning needs policy.

Sources: OwnerAuthenticator and bearerTokenAuthenticator, readTokenMapping, productForOwner, rejectCredentials; SUC-6, 7, 10, 11.

D4 · One Node.js process, native HTTP, SQLite local persistence

Problem: the implementation needs a running interface and retained state. Selected approach: native node:http, TypeScript run by Node, and a local SQLite database through Node's built-in driver. Status: accepted for one workflow process on one host-local disk.

Documented rationale: ADR 0002 selects transactional local persistence without operating a database server. Alternatives and trade-offs — mentor analysis: a web framework can supply routing/error conventions but adds dependencies; native HTTP keeps the present surface small while leaving those concerns handwritten. PostgreSQL could support coordinated distributed writers and richer operations, but requires a server and deployment contract. JSON is directly inspectable and has little setup, but blocks on full-file I/O and has no transaction/locking contract.

Risks and limits: this is not a distributed-writer design, and it does not add a backup or power-loss recovery protocol. A later deployment with multiple application hosts or workers must make a separate server-database decision before coordinating attempts.

Sources: runtime/dependencies, compiler settings, Workflow. Relevant tickets: SUC-6, 7, 10, 11, 13, 15.

D5 · Replaceable integrations, distinct declarations and activation

Problem: the same workflow must operate across products without tying business rules to one tracker, runner, or preview vendor. Selected approach: configurable references and replaceable integrations; a server-controlled ticket lookup seam exists today. Status: documented direction; most adapters and activation are planned.

Documented rationale: SUC-5 requires reuse across products, and ADR 0001 separates capability declarations from actual SUC-11 verification/activation. ADR 0002 requires the server-side finder instead of trusting request-provided ticket matches. SUC-8 specifies Linear as the first tracker, narrowing the parent specification for that adapter.

Alternatives and trade-offs — mentor analysis: hard-code one vendor for an initial end-to-end pilot, or define adapters around each capability. Hard-coding reduces initial interface work but spreads vendor assumptions; replaceable adapters require clear contracts and error semantics. Do not create interfaces for imagined variation without a concrete need.

Limits: current finder is synchronous and defaults to undefined; no real lookup is wired in start.ts. All configured integrations currently need both declared limit capabilities, which may not fit non-runner adapters. Capability-specific contracts and “lookup unavailable” handling remain open. Sources: ExistingTicketFinder, IntegrationReference; ADRs 0001/0002; SUC-8, 11, 12, 15, 16.

D6 · Unique customers, current-week precedence, rolling fallback

Problem: repeated messages should not inflate demand; quieter weeks should not erase recent evidence. Selected requirement: count each customer once per candidate from eligible source records; current week first, rolling window only when no current-week candidate crosses threshold. Defaults: three customers and current week plus three preceding weeks, configurable per product. Status: planned SUC-8/9.

Documented rationale: the SUC-5 problem statement explicitly identifies repeat-message inflation and loss of accumulated demand. Alternatives and trade-offs — mentor analysis: message counts reward volume; lifetime totals keep stale demand forever; weighted recency may be nuanced but harder to explain. The specified rule is auditable but sensitive to identity quality, calendar boundaries, and a threshold that may fit some products poorly.

Limits: threshold/window fields are not in today's ProductProfile; week start, inclusion boundaries, goal-alignment rubric and scope estimate are not fully defined. No evaluator exists. Sources: SUC-8, SUC-9.

D7 · Version-bound approval and fresh approval after a stop

Problem: qualification, ticket edits, and a resumed attempt must not silently authorize additional scope or spending. Selected requirement: only configured approver approval of settled ticket scope/acceptance criteria authorizes implementation; material edits invalidate it; stopped attempts require renewed approval. Status: planned SUC-10/11/14.

Documented rationale: SUC-5 user stories 26, 27, 34 explicitly explain preventing reuse of old approval after changes and keeping continuation deliberate. Alternatives and trade-offs — mentor analysis: approve a mutable ticket label, an immutable ticket revision, or a digest of material fields. Labels are easy but can drift from approved content; immutable revisions/digests are more precise but require a definition of “material,” race handling, and external tracker synchronization.

Limits: no version algorithm, approval ledger, role model, or invalidation protocol has been chosen in code. Approval deadline semantics across later weekends also need precision. Sources: SUC-10, SUC-14.

D8 · Bounded, deduplicated attempts with reviewable progress

Problem: an autonomous ticket can consume unlimited time/money or start twice on repeated events. Selected requirement: measurable enforced runtime/spending limits, budget checks before metered work, allowed time window, one active approved attempt, and saved draft work on stops. Status: planned SUC-11–14.

Documented rationale: SUC-5's problem statement and execution decisions require bounded autonomous work and a reviewable result before deployment. Alternatives and trade-offs — mentor analysis: best-effort timers and after-the-fact spend reports are easy but do not satisfy those enforcement requirements. A controlled runner with usage reservation/cancellation and a durable attempt claim can provide stronger guarantees, at the cost of adapter capability checks, crash recovery, and coordination.

Limits: attempt schema, atomic reservation, cancellation, usage reporting latency, currency/unit, and continuation budgeting remain unresolved. Saving a draft can itself fail; runner contract must specify recovery. Sources: SUC-11, SUC-13, SUC-14.

D9 · Delivery, rather than merge, determines fulfillment

Problem: merged code may not reach customers, and shipped scope may satisfy only part of a request. Selected requirement: verified release signal or explicit owner confirmation; retain original feedback and audit links; retire only satisfied scope and update inventory. Status: planned SUC-15.

Documented rationale: SUC-5 user stories 18, 19, 36, 37 explicitly distinguish confirmed customer delivery, unmet extensions, and current inventory. Alternatives and trade-offs — mentor analysis: marking every linked message fulfilled on merge is simpler but violates the requirement and hides partial demand. Explicit evidence is more accurate but introduces fulfillment interpretation, signal verification, idempotency, and transactional update questions.

Limit: current candidate fulfilled comparisons describe existing inventory; they are not a delivery ledger. Sources: SUC-15, ADR 0002.

D10 · Test observable workflow behavior with controlled integrations

Problem: provider calls and real weekends make tests slow and unstable; helper-call assertions can survive while product behavior is wrong. Selected direction: test the workflow's observable outputs, control external adapters and time, and add adapter contract checks where needed. Status: HTTP seam and controlled ticket finder implemented; controllable clock and full orchestration coverage planned.

Documented rationale: SUC-5 proposes a controllable clock to test windows and deadlines without waiting; published-tickets.md records user approval of the included testing approach. Alternatives and trade-offs — mentor analysis: test every helper, or only use live integrations. Helpers may aid narrow logic checks but should not replace workflow evidence; live integration checks reveal compatibility but require authorization and repeatable fixtures.

Limits: all seven current HTTP tests pass; they do not establish crash recovery, restart persistence, all ownership combinations, real integration behavior, or any planned end-to-end build. Typechecking checks types, not runtime contracts. Sources: current tests; SUC-6–16.
