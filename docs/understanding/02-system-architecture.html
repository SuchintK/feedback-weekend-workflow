02 · System architecture

Evidence reviewed 9 October 2026 · branch feature/SUC-7-group-feedback · commit b80de3d0816df80869251b8550d1ccae07236eb4. This is a branch snapshot; merge and deployment status were not verified.

The current application is one Node.js process with an HTTP adapter, one workflow module, and one SQLite state file. The planned architecture extends that workflow with evaluation, approval, execution, scheduling, review, and delivery responsibilities. The specification does not require those responsibilities to become independently deployed services.

Current architecture — implemented on this branch

Module / dependency Responsibility and why it exists Evidence
Startup Reads the token-to-owner map, data directory, and port; composes the server. Keeps deployment configuration outside feedback. start.ts; WORKFLOW_AUTH_TOKENS, WORKFLOW_DATA_DIRECTORY, PORT. Defaults: .data, 3000, loopback bind.
HTTP adapter Parses requests, derives owner from verified bearer token, validates payload shapes, selects a workflow operation, serializes responses. createWorkflowServer, bearerTokenAuthenticator. Authentication defaults to denial if no authenticator is supplied.
Workflow module Owns business rules: product access, credential checks, readiness, evidence linkage, inventory verification, candidate reuse. Centralizes invariants across requests. Workflow. Storage and rules currently share this module.
SQLite persistence Retains context between requests with transactions and foreign keys, without a database server. Workflow uses Node's built-in SQLite driver. No database server, ORM, or queue is required.
Ticket lookup seam Lets the trusted server supply an existing-ticket match rather than accepting a client's asserted ticket ID. ExistingTicketFinder(product, underlyingNeed); synchronous function. Controlled adapter in tests; default returns undefined.
Native test runner and TypeScript Exercise observable HTTP outcomes and check types without a framework or transpilation build. package.json, tsconfig.json, test/server.test.ts. Node >=24; installed runtime checked as v26.3.0.

Public interfaces and communication

HTTP request Workflow operation Successful response
POST /products registerProduct 201 product + readiness
PATCH /products/:id updateProductProfile 200 product + readiness
POST /products/:id/feedback submitFeedback 201 feedback record
GET /products/:id inspectProduct 200 product + readiness + feedback; candidates are not included
POST /products/:id/inventory-verification verifyInventory 200 reviewed inventory + repository URL + documentation references
POST /products/:id/analysis analyzeFeedback 200 inventory + submitted feature candidates + bugs, each with original evidence

Each operation is request/response; no event bus or background worker is implemented. GET / is a public explanatory HTML page. Every product route requires authentication, including feedback intake. The root page is not a product setup form.

Persistent data relationships

A candidate can reference several messages. Reuse compares candidate key or exact supplied underlying-need text within the product; there is no semantic similarity engine. A single analysis request disallows assigning a feedback ID twice. Across separate analyses, the code does not enforce one global candidate assignment for every feedback ID. The desired treatment of a message containing several needs remains an open question.

Readiness is configuration; execution has additional gates

Signal Current meaning Additional evidence / planned gate
Registered Identity, verified owner, feedback intake recorded. May collect feedback with incomplete analysis/build configuration.
Analysis-ready Goals, repository identity/URL, documentation references, nonempty inventory present. Analysis additionally needs a matching owner-verified inventory snapshot. Readiness itself does not assert verification freshness.
Build-ready Analysis settings plus default branch, ticket destination, approver, validation/preview instructions, restrictions, timezone/schedule, positive runtime/spending limits, declared integration capabilities. SUC-10/11/13 still require version-specific approval, actual enforceability/activation, allowed time, policy review, and duplicate prevention. No build operation exists today.

Current build readiness requires preview instructions even though the product spec describes previews “where applicable.” Each configured integration must declare both runtime-limit and spending-limit. These are current validation rules, not evidence that a real runner can honor them. Schedule times receive basic validation; buildWindow is only nonempty text.

Planned workflow architecture — responsibilities, not approved file layout

SUC-5 specifies replaceable integrations without selecting AI, hosting, or runner vendors. SUC-8 specifically calls for Linear as the first proposal tracker. The fact that this project's own planning uses Linear does not mean the application currently connects to Linear. GitHub PR links are implementation-work evidence, not an implemented application runner.

Architectural boundaries worth learning

  • Evidence and authority: feedback may contain instructions, but it is stored as text and cannot alter profile configuration or grant build permission.
  • Owner identity and customer identity: the bearer token identifies the operator; customerId attributes evidence. A customer ID is not login authority.
  • Workflow and adapters: shared decisions should not depend on a tracker or preview vendor. Only a ticket-finder seam is implemented; other integration interfaces remain design work.
  • Current and delivered scope: an inventory match during analysis is different from the future delivery ledger that retires feedback.
  • Review and release: building, testing, and opening a PR prepare review; they do not authorize deployment.

Limits of this implementation

File replacement reduces exposure to a partially written JSON destination, but does not supply multi-process transactions, file locking, backup, or power-loss durability guarantees. Synchronous full-file I/O can block the Node event loop as data grows. Persisted JSON is cast to types without full schema validation. The HTTP adapter reports unclassified errors as 400; storage outages are not separately modeled as server errors.

Inventory verification compares URL, ordered item strings, and ordered documentation-reference strings. It does not capture a repository commit or fetch file contents. A real async ticket adapter also needs a suitable interface; the current finder is synchronous. These are design questions, not changes made by this task.

Suggested code tour

  1. start.ts: locate trusted inputs and dependency wiring.
  2. server.ts: trace POST /products/:id/analysis through authentication and shape validation.
  3. workflow.ts: read types and requirements, then analyzeFeedback, productForOwner, SQLite queries and transactions.
  4. test/server.test.ts: compare the grouping test's submitted interpretations with the returned evidence.
