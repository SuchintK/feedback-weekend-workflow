Evidence freshness: should verification bind to repository content? inventoryEvidence stores URL and ordered documentation/inventory strings. hasCurrentInventoryVerification compares those values. It does not capture commit, content, provider/reference, or verification time. analysisReady does not include this comparison. Clarifies the strength of the SUC-7 verification gate and downstream SUC-8 eligibility. Changing remote content behind an unchanged URL is not detected. Decide whether string acknowledgement is sufficient or commit/content evidence is required. Storage: what concurrency and recovery guarantees are required? Workflow stores Product and Feedback records in local SQLite. The accepted process model is one workflow process on one host-local disk. Relevant to durable SUC-6/7 data and future attempt, scheduler, continuation, and delivery records in SUC-11, SUC-13, SUC-14, SUC-15. SQLite transactions, restart persistence, duplicate registration, and owner isolation are covered. Backup, power-loss recovery, and coordinated distributed writers remain outside the selected operating model. Revisit the storage ADR before introducing multiple application hosts or distributed workers. Define backup and power-loss recovery requirements before treating the local file as an operational database service. Accepted — local-process contract
Failures: which errors should callers retry, and what details should be exposed? catch block maps generic exceptions to 400 with their message. validateExistingTicket explicitly uses 502 for invalid id/title, but a thrown finder or filesystem exception is generic. Caller diagnosis and retry behavior for SUC-6/7 and later external integrations. The classification is confirmed by code; actual storage failure behavior has not been exercised here. Define public error categories and retry semantics; distinguish malformed input, integration outage, and storage failure. Verify error responses and state preservation through controlled failures. Open — failure contract
Credential handling: what precise guarantee can documentation make? README says credentials are never accepted in profiles, feedback, or tickets. rejectCredentials uses patterns; submitFeedback scans originalText and constrains sourceReference but does not scan every text field. Analysis strings and ticket finder id/title have no credential scan. There is no ticket-writing implementation. Current documentation is broader than the implemented checks. Affects SUC-6/7 contracts and future ticket publication in SUC-8. This is a scope discrepancy, not evidence that secrets were submitted. Define supported input and redaction/rejection policy. Document the current heuristic precisely and add meaningful field/adapter tests if a stronger guarantee is required. Open — documentation/validation scope
Candidate lifecycle: how should owners inspect, revise, or retire durable analysis? analyzeFeedback unions feedback IDs, permits repeated evidence across separate requests, and returns only candidates in the current call. GET inspection excludes candidates. Bug output omits comparison/ticket details; no retirement or reassignment operation exists. Durable evidence management for SUC-7, demand evaluation in SUC-8, and selective retirement in SUC-15. Specify candidate retrieval, correction, identity, evidence reassignment, and delivery/retirement semantics. Decide whether bugs need visible ticket comparison. Test state across repeated analyses rather than assuming global uniqueness. Open — lifecycle interface
Test evidence: which missing cases are required for the current and next slice? Seven tests cover representative HTTP paths. No restart, storage corruption/failure, concurrent writers, real startup/finder wiring, complete buildReady, two-product isolation, or downstream lifecycle case exists. Many validation branches lack direct assertions. Bounds confidence for SUC-6/7 and acceptance planning for SUC-8–16. One test title mentions uncertain fulfillment while its assertions only check configuration isolation and blocked analysis; another test covers actual uncertainty. Map acceptance criteria to assertions. Add focused observable tests for required missing guarantees, including verification invalidation, cross-product IDs, finder failure, and candidate conflicts; keep integration doubles controlled. Open — coverage plan
Input semantics: which values should be rejected versus stored as incomplete? submitFeedback uses Date.parse despite an ISO-8601 error message. Profile validation accepts non-empty timezone/time strings, while readiness separately rejects invalid zones or non-HH:MM times. HTTP rejects unknown profile/repository fields but ignores some extra fields elsewhere. API expectations for SUC-6/7 and scheduling in SUC-13. Current behavior is broader or differently staged than some error wording implies. Specify canonical date formats, normalization, incomplete-setting behavior, and unknown-field policy. Align parsing, readiness, and user-facing messages; test explicit valid and invalid examples. Open — validation consistency
