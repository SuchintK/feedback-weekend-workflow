Domain terms

Meaning, example, and current implementation are distinct
Term Meaning Example Implementation and ticket context
Product The unit of workflow configuration, feedback, and ownership. Atlas has its own goals and feedback evidence. Product has id, name, ownerId, and profile; SUC-6.
Owner The verified actor authorized to manage a registered product. owner-atlas may inspect Atlas. ownerFrom derives identity through the authenticator; productForOwner checks exact owner equality. Use “owner,” not “customer,” for this authority; SUC-6.
Customer The person or organization whose feedback expresses product demand. customer-42 requests spreadsheet exports. Feedback.customerId is caller-supplied evidence, not an authenticated workflow principal. Stable identity will matter to distinct-customer counting in SUC-8.
Product profile The durable configuration describing a product's context and operating constraints. Goals, repository references, inventory, approver, and limits. ProductProfile permits incremental completion; feedbackIntake is required at registration. ADR 0001; SUC-6.
Feedback intake The configured source of a product's feedback. “intercom” identifies the intake. Currently a required text field; no intake connector is activated. Feedback enters through authenticated HTTP submission; SUC-6.
Feedback A traceable original customer message retained as evidence. “Please export reports to a spreadsheet,” with customer, source, and date. Feedback, submitFeedback preserve originalText and generate per-product sequential IDs. No submission deduplication is implemented; SUC-6/7.
Source reference A locator connecting feedback to its original source. intercom:conversation:987 sourceReferencePattern accepts a colon-separated identifier grammar, not an arbitrary URL; SUC-6.
Inventory The product's declared existing functionality. CSV export. ProductProfile.inventory is a non-empty list of text when supplied; no repository scanner generates it. SUC-7.
Inventory verification The owner's acknowledgement of the inventory against repository and documentation evidence. The owner acknowledges CSV export with the configured repository and README reference. verifyInventory stores owner/product IDs, URL, inventory items, and documentation references. There is no commit hash or remote-content verification; SUC-7, ADR 0002.
Analysis readiness Completeness of the configured context required for analysis. Goals, repository identity, documentation references, and inventory are present. analysisRequirements, readiness compute analysisReady. Current inventory verification is an additional analyzeFeedback gate; the flag itself does not establish freshness; SUC-6/7.
Build readiness Completeness of declared configuration required before build activation can be considered. The profile includes branch, approver, instructions, schedule, restrictions, limits, and integrations. buildOnlyRequirements adds predicates to analysis readiness. It does not establish approval, verified integrations, or an available runner; SUC-11 remains Backlog.
Underlying need The product outcome shared by one or more requests. Export reports in a spreadsheet-compatible format. CandidateInput.underlyingNeed is supplied by the owner; reuse compares exact strings. There is no semantic normalization or AI grouping engine; SUC-7.
Candidate A durable interpretation of a need linked to supporting feedback. spreadsheet-export links two original requests. Candidate, analyzeFeedback store key, need, kind, feedback IDs, and optional match. Feature and bug are separate kinds; SUC-7.
Feature candidate A candidate for new or extended product functionality. Add native spreadsheet export beyond existing CSV export. Each feature input requires a comparison outcome. asFeatureCandidate returns match details and original evidence; SUC-7, later SUC-8.
Bug A candidate describing a failure of expected behavior. Password reset returns an error. Owner-supplied kind; matches are optional. asBugCandidate returns key, need, and evidence without match or existing-ticket details; SUC-7.
Fulfillment match The comparison between a candidate need and existing functionality. CSV export may satisfy some spreadsheet requests. MatchDisposition, validateMatch validate the owner's supplied comparison. Ticket lookup is separate; SUC-7.
Unmet The need remains unsatisfied by the compared functionality. No saved report filters exist. unmet is a match disposition. Future proposal eligibility also requires no checked existing ticket; SUC-7/8.
Fulfilled Existing functionality satisfies the compared need. CSV download satisfies a request for CSV download. fulfilled requires an existingFunctionality value exactly present in verified inventory; SUC-7. This comparison is distinct from future delivery confirmation in SUC-15.
Unmet extension An additional need beyond existing functionality that remains unsatisfied. CSV exists, but native XLSX output is still requested. unmet-extension requires a referenced inventory item; SUC-7/8.
Uncertain A comparison whose fulfillment cannot yet be settled. Does “spreadsheet export” mean CSV or native XLSX? uncertain requires a non-empty clarification question and suggested interpretations. It does not trigger a customer message or approval; SUC-7, later SUC-10.
Existing ticket A previously tracked work item addressing the candidate's need. SUC-42 tracks spreadsheet export. ExistingTicketFinder supplies id/title server-side. Startup currently uses a finder returning undefined; no ticket existence check is performed there. A ticket is not proof of delivery; SUC-7/8.
Integration declaration Configuration describing an external capability intended for the workflow. A runner endpoint declares runtime-limit and spending-limit capabilities. IntegrationReference, hasDeclaredLimitCapabilities check URL and strings. Verification and activation are future SUC-11 behavior, not established by the declaration.
Demand Customer support for an eligible feature within an evaluation period. Three distinct customers support one feature this week. Future SUC-8 counts customers, not messages; SUC-9 adds fallback. Threshold and rolling-window fields are absent from ProductProfile.
Proposal A scoped feature recommendation presented for a decision. A ticket describes spreadsheet export, evidence, acceptance criteria, and exclusions. Future SUC-8 publication behavior; no proposal record or route exists at this baseline.
Approval Explicit authorization by the configured approver for a particular scope version. The approver accepts version 3 of a ticket's scope. Future SUC-10; a configured approver string or buildReady flag is not approval evidence.
Build attempt One bounded execution of approved implementation work. An approved run stops at its runtime limit and preserves progress. Future SUC-11; SUC-14 adds fresh approval and distinct continuation attempts.
Review package The evidence and output a reviewer needs to assess implementation work. A draft PR, validation results, acceptance evidence, and preview reference. Future SUC-12; no validation or preview executor is implemented.
Delivery Verified availability of implemented scope that satisfies identified demand. The owner confirms that released XLSX export satisfies linked requests. Future SUC-15; a merge or draft PR alone does not confirm delivery.

Technical learning terms

General engineering terms used to explain this implementation
Term Meaning Example and component
HTTP route A method and URL pattern mapped to an operation. createWorkflowServer maps POST /products/:id/analysis to analyzeFeedback. Unknown method/path combinations return 404.
Authentication / authorization Authentication identifies the caller; authorization decides access to a resource. bearerTokenAuthenticator resolves a token; productForOwner compares product ownership. Missing verified identity gives 401; wrong owner gives 403.
Bearer token A credential presented by the caller to establish identity. WORKFLOW_AUTH_TOKENS maps opaque tokens to owner IDs; bearerTokenAuthenticator matches the Bearer header. These are server configuration, not product-profile fields.
Dependency injection / seam A boundary where a caller supplies a behavior instead of hard-coding it. OwnerAuthenticator and synchronous ExistingTicketFinder are function seams; tests inject a controlled ticket finder.
Runtime validation Checks on actual values received while the program runs. asProfile rejects unknown profile keys; validateMatch checks inventory references. Types alone do neither.
TypeScript / typecheck Static checking of program types before execution. strict, noEmit; npm run typecheck. Analysis result arrays are typed unknown[], limiting typed result consumers.
ESM / NodeNext JavaScript module conventions and matching TypeScript module resolution. type: module, module: NodeNext, explicit .ts imports, and Node ≥24 execute erasable TypeScript directly.
Persistence / serialization Keeping state across process lifetimes by encoding it for storage. write serializes the whole StoredWorkflow as JSON. Restart behavior is intended by this design but not tested in the current suite.
Atomic replacement Replacing a visible file through a rename after preparing its replacement. workflow.json.tmp is written then renamed. This pattern does not by itself provide fsync-based durability, reader transactions, or multiple-writer coordination.
Locking / concurrency Coordination of overlapping access to shared state. Synchronous operations keep one event-loop operation contiguous, but there is no cross-process lock around read/modify/write. Concurrent-writer behavior is unverified, not an observed incident.
Snapshot / freshness A captured set of evidence values, and whether it still matches the required current evidence. inventoryEvidence captures URL and ordered strings. hasCurrentInventoryVerification compares those strings, not repository commits or content.
Idempotency / deduplication Idempotency makes repeat operations have no additional intended effect; deduplication recognizes repeated records. Analysis reuses exact matching needs and unions feedback IDs. Feedback POST always appends. Neither establishes future scheduler or proposal idempotency.
HTTP error semantics The meaning assigned to response status and error payload. catch block preserves WorkflowError.status; generic errors become 400 with their message. validateExistingTicket uses 502 for invalid ticket fields.
Integration test / test double A test across connected components; a controlled substitute for an external behavior. withServer uses HTTP and file storage; a supplied finder returns SUC-42 without a tracker call.
Time window / currency contract Explicit rules for time boundaries and monetary units. Timezone and HH:MM readiness predicates exist; week start, build-window grammar, and spending currency are unsettled. See open contracts.

Component and interface index

Locate the code responsible for a concept
Component Responsibility and public surface Boundary to remember
start.ts Reads WORKFLOW_DATA_DIRECTORY (default .data), PORT (default 3000), and required WORKFLOW_AUTH_TOKENS; listens on 127.0.0.1. No exported API; does not wire a real finder. Invalid token mapping fails startup.
server.ts Exports createWorkflowServer, bearerTokenAuthenticator, OwnerAuthenticator, and re-exports ExistingTicketFinder. Provides six JSON routes plus a public HTML placeholder at /. Factory authentication defaults to denial; default finder returns undefined. HTTP parsing is stricter than calling typed Workflow methods directly.
Workflow Public operations: registerProduct, updateProductProfile, submitFeedback, inspectProduct, verifyInventory, analyzeFeedback. Owns validation, authorization, readiness, and file persistence. Owner ID is trusted input at this internal boundary. inspectProduct returns product/readiness/feedback, not candidates; analysis returns candidates submitted in that call.
Exported domain types RepositoryContext, IntegrationReference, ProductProfile, Product, Feedback, Readiness, MatchDisposition, ExistingTicket, ExistingTicketFinder, CandidateInput, AnalysisInput; also isMatchDisposition and WorkflowError. Candidate, CandidateMatch, InventoryVerification, and StoredWorkflow are internal types. Readiness is computed rather than persisted.
StoredWorkflow and file helpers Four collections: products, feedback, candidates, inventoryVerifications. read defaults missing collections; write replaces the complete file. No schema version, stored-shape validation, migration runner, locking, backup policy, or fsync protocol is implemented.
server.test.ts Seven HTTP scenarios use temporary storage, bearer identities, fetch, and a controlled finder. No restart, multi-process, real tracker, full buildReady, or downstream lifecycle test is present.
