Solid sequences below describe either observed code or explicitly labeled requirements. Planned participants are responsibilities to implement, not existing processes, routes, or data tables. Read the architecture first if the module names are unfamiliar.

1. Register and incrementally configure a product — implemented

Trigger: authenticated owner submits POST /products, then optional PATCH /products/:id. Input: product ID, name, profile; owner identity comes from the server-side token map. Transformation: request shape checks, credential rejection, profile merge on update, readiness calculation. Persistence: Product in SQLite. Response: 201 registration or 200 update, with product and missing readiness fields.

Failures: missing/unrecognized bearer token 401; invalid profile or missing intake 400; duplicate product ID 409; update of unknown product 404 or another owner's product 403. A write failure does not return a successful registration. Unclassified failures currently become 400 at the HTTP adapter. Sources: registration/update routes, registerProduct, updateProductProfile, mergeProfile, readiness; SUC-6.

2. Record original feedback and inspect it — implemented

Trigger: owner submits structured feedback on behalf of a customer. Input: stable customer ID, original text, credential-free source reference, received date. The product ID is taken from the route. Transformation: validation and generated feedback ID; original text is preserved if accepted. Persistence: Feedback row. Response: 201 feedback object, then 200 inspection result on GET.

Failures: malformed required fields or invalid date/source/credential pattern 400; unauthorized product access 403; unknown product 404; unauthenticated 401. HTTP bodies above 1 MB return 413. Date parsing uses Date.parse; despite the error message, it is not a strict ISO grammar validator. Source references use a constrained scheme such as intercom:conversation:987, rather than arbitrary URLs. Feedback submission has no deduplication key; repeating a successful POST creates another record. Distinct-customer scoring will be a later responsibility, not intake deduplication.

Sources: submitFeedback, inspectProduct, sourceReferencePattern; traceable feedback and instruction-in-text tests; SUC-6.

3. Verify inventory and persist interpreted candidates — implemented branch behavior

Trigger: owner first POSTs an empty object to inventory verification, then submits explicit candidate groups and feature-match outcomes to analysis. Transformation: compare current inventory snapshot, validate feedback ownership, validate comparison outcomes, perform trusted ticket lookup, reuse a candidate by key or exact underlying need, deduplicate linked feedback IDs. Persistence: InventoryVerification and Candidate arrays. Response: 200 inventory, feature candidates, and bugs with linked original evidence; only candidates submitted in this request are returned.

Failures: analysis settings missing or snapshot no longer matches 409; candidate key redefined or kind conflicts 409; missing comparison for a feature, invalid linked feedback, duplicated assignment in one request, unknown inventory reference, or uncertainty without question/options 400. An invalid ticket-finder result returns 502. A finder that throws an untyped error gets the adapter's generic 400. No state snapshot is written when candidate validation or lookup fails before write.

Matching verification checks ordered inventory and documentation lists plus repository URL and owner. It does not read the repository. Changing those references requires reverification before analysis. A change to underlying file contents at the same references is not detected. The default finder cannot distinguish “no ticket” from “lookup not configured”; SUC-8 must resolve that distinction before claiming a checked absence.

Sources: verifyInventory, analyzeFeedback, validateAnalysisInput, validateMatch, hasCurrentInventoryVerification; ADR 0002; SUC-7.

4. Evaluate demand and publish a proposal — planned SUC-8/9

Trigger: weekly evaluation; later invoked at the configured proposal time. Participants: evaluator, persisted evidence/candidates, product goals/configuration, ticket publisher. Transformation: select eligible unmet features or extensions without checked existing tickets; filter by time and fulfillment; count unique customers per candidate; qualify and rank. Persistence required: reusable proposal/ticket identity and evaluation evidence. Exact schemas and routes are unresolved. Result: one proposal plus alternatives, or a visible no-qualifying-demand outcome.

Failures to design: tracker unavailable, ambiguous eligibility, stale checked ticket state, undefined calendar week, and duplicate events. Required behavior includes duplicate prevention and explainable counts; atomic publication/retry mechanics are not selected. Defaults of three customers and four calendar weeks are specified, but profile fields for these options are not implemented. Sources: SUC-8, SUC-9, candidate eligibility contract.

5. Approve, execute, review, and handle a stop — planned SUC-10–14

Trigger: configured approver explicitly approves settled ticket scope; a permitted manual or scheduled start follows. Transformation: verify version, authority, policy, time, configuration, active attempt, and enforceable limits; perform bounded work and assemble validation evidence. Persistence required: approval evidence, ticket version, distinct attempt identity, usage/progress, PR/review references. Schemas and runner vendor are unresolved. Result: reviewable PR and applicable preview, or preserved draft with blockers and remaining work.

Failure requirements: wrong approver, unresolved scope, invalidated version, missed deadline, out-of-window start, unsupported limit enforcement, exhausted runtime/spending, failed required checks, scope expansion, and duplicate starts/resumptions must not silently proceed. A retained proposal may be reconsidered later under applicable approval rules. Fresh approval and a distinct continuation attempt are required after a stop. Crash recovery, atomic claims, and cancellation mechanics remain design decisions.

Sources: SUC-10, SUC-11, SUC-12, SUC-13, SUC-14.

6. Confirm delivery and retire satisfied demand — planned SUC-15

Trigger: verified configured release signal or explicit owner delivery confirmation. Transformation: compare delivered scope against linked evidence, identify complete and partial satisfaction, retain unmet extensions, escalate uncertainty. Persistence required: delivery identity/scope, fulfillment audit links, updated inventory. Result: later evaluations exclude only satisfied evidence, with original feedback retained.

Failures to handle: unverified release source, repeated signals, wrong product, partially delivered scope, ambiguous satisfaction, interrupted inventory/fulfillment update. Idempotency and retained unmet demand are explicit requirements; the transaction design and delivery-verification protocol remain unresolved. See SUC-15.
