A product owner receives twenty messages about exports, several about a broken password reset, and a few requests for functionality that already exists. This project turns those messages into traceable product evidence and, eventually, one explicitly approved, bounded weekend implementation.

The workflow is the product. It can be configured for Atlas, Beacon, or another customer product. Atlas is an illustrative product used in tests, not a selected production pilot. We are building reusable coordination around those products, rather than implementing their requested features in this repository.

People and responsibilities

  • Product owner: registers the product, supplies goals and evidence, verifies inventory, interprets feedback, and resolves uncertainty.
  • Customer / feedback submitter: supplies attributable evidence. The intended intake is structured. Current HTTP submission requires the registered owner's authentication; a direct public customer form is not implemented.
  • Configured approver: authorizes a particular ticket version. The owner and approver can be conceptually distinct; a separate approver workflow is planned in SUC-10.
  • Reviewer: inspects a pull request, validation evidence, and applicable preview before a separate deployment decision.

User journeys

1. Start learning demand before enabling builds — available today

  1. The owner registers Atlas with its name and feedback-intake reference.
  2. The service returns missing analysis and build settings; feedback can already be stored.
  3. The owner adds goals, repository/documentation references, and inventory. Analysis readiness becomes true.
  4. The owner verifies the current inventory snapshot and submits interpreted request groups.
  5. The service preserves evidence, separates bugs, and returns comparison outcomes. A snapshot verification is an owner attestation, not an automated repository scan.

2. From repeated requests to one proposal — planned

Alice sends three messages for native spreadsheet export; Bob and Chen each send one. That is five messages but three customers. If all evidence is eligible this week, the default threshold is met. The evaluator ranks it against other candidates, shows alternatives, and publishes one proposal with scope, acceptance criteria, exclusions, assumptions, and evidence. An existing CSV export may satisfy some wording; uncertain matches require clarification.

If nobody qualifies this week, SUC-9 checks the current week plus the preceding three weeks by default. Alice still counts once across the whole window. A qualifying but unapproved proposal does not trigger fallback. Nothing qualifying means a visible skip.

3. Approve, build, and review — planned

The configured approver settles scope and explicitly approves version V1. A material scope edit to V2 invalidates that approval. The runner rechecks configuration, authority, review requirements, time window, and enforceable budgets. It preserves a draft pull request on interruption; validation and applicable preview make the result reviewable. A stopped attempt needs fresh approval to continue. No step here grants deployment permission.

4. Confirm fulfillment — planned

When native spreadsheet export reaches customers, a verified delivery signal or explicit owner confirmation records delivered scope. Only satisfied feedback leaves future demand calculations; records remain linked for audit. A request for scheduled spreadsheet emails remains unmet. A pull request or merge alone cannot retire either request.

First lesson: configuration, evidence, and authority

Configuration says where and under what constraints work could happen. Evidence explains what customers need. Authority permits a specific operation. Customer text belongs to evidence; a complete Product Profile is configuration; approval of a ticket version is planned authority for a bounded build.
