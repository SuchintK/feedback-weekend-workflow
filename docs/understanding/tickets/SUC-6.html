SUC-6: Register a product and collect traceable feedback

Linear status: Done · Evidence date: 2026-10-09 · Local branch: feature/SUC-7-group-feedback · HEAD: b80de3d.

Requirements and status come from the live Linear evidence supplied by the main agent. Local behavior is based on repository inspection, not a fresh test run or proof of merge. Read the original SUC-6 issue; parent: SUC-5. Source user stories: 1, 2, 3, 4, 5, 6, 7, 39.

Problem and why it matters

Recurring feedback work needs a stable product context. A customer request must retain its wording, customer identity, source, and received date so later grouping and demand counts can be explained. Setup must also retain the owner’s repository, goals, and operating constraints across requests.

The live amendment makes an authenticated, persistent owner workflow the primary interface. A development CLI would not satisfy that interface contract. Owners can begin with partial configuration, but missing evidence or operating settings must remain visible.

Architecture connection

ADR 0001 chooses one durable, credential-free product profile because recurring work and the SUC-7/SUC-11 handoff need stable context. Server-verified identity establishes ownership; request data cannot choose its own authority. Integration declarations describe intended capabilities and require later verification before activation.

Source acceptance criteria

The following criteria reproduce the supplied Linear wording. Checkbox completion is not inferred from the issue status.

  • Provide a usable submission and inspection interface with durable feedback records containing product ID, stable customer ID, original text, source reference, and date.
  • Keep records and access isolated by product, and keep credentials outside feedback and tickets.
  • Store per-product goals, integrations, approver, inventory, schedule, validation instructions, restricted areas, runtime, and spending settings; report missing build settings before activation.
  • Demonstrate submission, retrieval, configuration validation, and cross-product isolation through observable workflow tests.

SUC-6 acceptance criteria amendment

  • Provide authenticated owner setup and inspection plus structured feedback intake; do not make a local CLI the primary product interface.
  • Persist the complete product profile above, with repository and default branch as first-class build configuration rather than an unstructured integration field.
  • Persist durable feedback with product ID, stable customer ID, original text, credential-free source reference, and received date; isolate records and access by product.
  • Return visible registered, analysis-ready, and build-ready status with precise missing fields; only build-ready products can enable scheduled implementation.
  • Demonstrate product setup, feedback submission/retrieval, readiness transitions, repository-context requirements, credential exclusion, and cross-product isolation at the observable workflow seam.

Current implementation versus planned work

Linear says Done. The branch provides authenticated registration, profile updates, feedback submission, and inspection over HTTP. Workflow persists products and feedback in SQLite; inspection returns readiness and precise missing-field lists. Authentication uses a server-side bearer-token mapping. Historical changes replaced the one-request CLI in 99c9018 and hardened authentication and incremental setup in 013a199.

Tests exist for setup, feedback, ownership, and readiness. They were inspected, not run for this documentation. Later build and scheduler behavior is absent, so their future use of the setup contract is not yet demonstrated locally.

Proposed approach — mentor analysis

This section explains a possible implementation; it is not an accepted design, a new requirement, or authorization to build.

Follow one registration request from HTTP authentication into profile validation, owner binding, durable storage, and response readiness. Then trace a partial update and ask which missing fields disappear. Keep the distinction between saved configuration and activated capability explicit when reasoning about successors. A full profile is a handoff contract; a successful save is not evidence that an external runner can enforce its limits.

Durable state and readiness

Implemented durable state: a product has stable ID, name, authenticated owner, and profile. Feedback has ID, product ID, customer ID, original text, source reference, and received date. The store is local SQLite; the database selection is recorded in ADR 0002.

Readiness: registration requires identity, owner, and feedback intake. Analysis readiness requires goals, repository identity, documentation references, and inventory. Build readiness adds branch, destination, approver, validation/preview instructions, restrictions, schedule/timezone, positive limits, and declared integration capabilities. These flags do not represent approval or activated enforcement.

Concepts to learn

  • Authentication establishes identity; product ownership authorizes access to a particular record.
  • A durable domain contract survives requests even when the storage implementation changes.
  • Readiness is derived from evidence and configuration, while approval and integration activation are separate gates.

Alternatives and tradeoffs

A one-request CLI is convenient for development but loses the persistent owner interface selected by ADR 0001. A feedback-only namespace is smaller but forces later steps to rediscover repository context and constraints. SQLite supplies local transactions, while distributed-writer and deployment topology remain outside the accepted operating model.

Failure scenarios

  • A caller submits another owner’s product ID: inspection, updates, and feedback intake must reject unauthorized access.
  • A partial profile lacks repository evidence: analysis readiness must report the missing fields instead of implying existing functionality was checked.
  • An integration claims limit capabilities: the profile can retain that declaration, but SUC-11 still needs proof before running.
  • Credential values appear in configuration or feedback: exclude actual secrets while preserving ordinary customer wording.

Test strategy

Inspect the existing server tests for registration, submission/retrieval, profile completion, invalid identity/input, and cross-product access. Follow their requests and responses rather than testing private helper structure. Any future changes should preserve received dates and original wording across restarts and expose readiness transitions. Controlled external integrations and a controllable clock apply where relevant; no real integrations need activation to understand this ticket.
