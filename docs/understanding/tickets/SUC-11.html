SUC-11: Run one approved build within enforced limits

Linear status: Backlog · Evidence date: 2026-10-09 · Local branch: feature/SUC-7-group-feedback · HEAD: b80de3d.

Requirements and status come from the live Linear evidence supplied by the main agent. Local behavior is based on repository inspection, not a fresh test run or proof of merge. Read the original SUC-11 issue; parent: SUC-5. Source user stories: 3, 27, 30, 31, 33, 35, 38, 39.

Problem and why it matters

An approved feature still needs a bounded execution environment. The runner must target the configured repository, respect product authority and restricted areas, enforce time and spending constraints, and leave reviewable work when it stops. A declaration that an integration supports limits does not prove those limits can be measured and enforced.

Architecture connection

ADR 0001 explicitly assigns integration verification and activation to SUC-11. This ticket will join the planned version-bound approval contract from SUC-10 with the durable operating profile from SUC-6. It introduces the execution boundary consumed by review packaging and scheduling; neither a readiness flag nor a tracker label grants authority alone.

Source acceptance criteria

The following criteria reproduce the supplied Linear wording. Checkbox completion is not inferred from the issue status.

  • Recheck ticket-version approval, complete build configuration, product-scoped access, and restricted-area review before execution.
  • Use a controlled implementation runner for the configured repository; preserve changes as a draft pull request and summarize progress.
  • Enforce configured runtime, spending cap, and allowed build window; check remaining budget before further metered work.
  • Only activate integrations capable of measuring and enforcing their limits; stop and save progress when a limit is reached.
  • Prevent duplicate attempts for the same approved run; preserve failures without deploying or merging.
  • Verify an approved run and denied, duplicate, exhausted-budget, and exhausted-runtime runs through observable results and controlled runner/usage integrations.

Current implementation versus planned work

Backlog and absent locally. The profile and readiness checks retain repository branch, limits, restrictions, schedule, and declared integration capabilities. There is no implementation runner, capability activation, usage meter, runtime enforcement, attempt ledger, or draft-PR integration. A complete buildReady response therefore does not demonstrate an enforceable build.

Proposed approach — mentor analysis

This section explains a possible implementation; it is not an accepted design, a new requirement, or authorization to build.

As mentor analysis, validate current approval and configuration at the execution boundary, verify integration enforcement capability, review restricted-area policy, and persist an identifiable attempt before external work. Before each metered step, check remaining runtime, spending, and the allowed window. Save progress and a draft PR reference on stop or failure. Reconcile repeated requests against the same approved run rather than starting twice.

Runner selection, isolation, spend reservation for in-flight calls, cancellation guarantees, attempt identity, and recovery after a crash are unresolved. These choices need evidence and may warrant a future ADR under repository guidance; this page does not settle them.

Durable state and readiness

Proposed backlog state: an attempt record linking product, approved ticket/version, execution identity, verified integrations, start/stop outcome, resource usage, progress, and draft PR. Duplicate prevention and recovery require a durable claim or equivalent protocol, but its storage/locking design is not accepted yet.

Readiness: consumes build-ready configuration and current approval; verifies and activates declared integration capabilities before work. Activation is not implemented and should not be implied by existing readiness flags. Reaching a limit stops the attempt and preserves work; it does not grant extra budget or permission to merge/deploy.

Concepts to learn

  • A capability declaration is a configuration claim; activation requires operational verification.
  • Retry safety needs a durable attempt identity that survives crashes.
  • A spending cap requires checking future metered work, not only reporting cost after it happens.

Alternatives and tradeoffs

Post-hoc usage reports are easy but cannot enforce the cap. A single long runner call simplifies orchestration yet makes cancellation and remaining-budget checks harder. Smaller controlled steps improve observability at orchestration cost. In-memory duplicate flags are insufficient across restarts; the durable protocol remains to be chosen.

Failure scenarios

  • Approval changed or configuration became incomplete before start: deny execution.
  • An integration can report cost but cannot enforce its cap: do not activate it.
  • A repeated start request targets the same approved run: preserve one attempt.
  • Runtime, spending, or build window is exhausted: stop and save changes rather than continuing or merging.

Test strategy

Drive approved and denied runs through an observable boundary with controlled runner, usage, clock, and PR integrations. Simulate duplicate starts, budget exhaustion before another call, runtime exhaustion, out-of-window work, unsupported enforcement, and runner failure after partial changes. Assert a reviewable draft/progress result and no deploy or merge. Detailed crash recovery tests should follow the chosen attempt protocol.

Explain it back

  1. Why does buildReady not establish that a runner can enforce its limits?
  2. What must be rechecked immediately before execution?
  3. How can a spending check fail even when past usage is below the cap?
  4. What evidence must survive a stopped or duplicate run?
