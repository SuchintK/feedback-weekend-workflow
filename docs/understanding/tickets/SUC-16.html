SUC-16: Activate and verify the workflow for a second product

Linear status: Backlog · Evidence date: 2026-10-09 · Local branch: feature/SUC-7-group-feedback · HEAD: b80de3d.

Requirements and status come from the live Linear evidence supplied by the main agent. Local behavior is based on repository inspection, not a fresh test run or proof of merge. Read the original SUC-16 issue; parent: SUC-5. Source user stories: 1, 2, 3, 39.

Problem and why it matters

A workflow that works for one hard-coded product has not demonstrated reuse. Two products must complete the same process through configuration, with independent feedback, approvers, ticket destinations, inventory, usage, and scheduled attempts. This ticket tests the composition of the earlier boundaries rather than adding another product-specific branch of shared logic.

Architecture connection

The persistent product contract in ADR 0001 and evidence-backed candidates in ADR 0002 must remain scoped by product throughout the full lifecycle. Configuration is the variability boundary; controlled integrations enable repeatable proof before a documented, authorized pilot.

Source acceptance criteria

The following criteria reproduce the supplied Linear wording. Checkbox completion is not inferred from the issue status.

  • Activate two distinct product profiles through the established interface, supplying explicit schedules, limits, validation instructions, and scoped integrations.
  • Verify feedback-to-proposal-to-approval-to-review-to-delivery for both profiles, including rolling fallback and a stopped attempt.
  • Demonstrate that one product's feedback, approver, ticket destination, inventory, usage, and scheduled attempts cannot affect the other.
  • Use controlled external integrations for repeatable tests and a documented, authorized pilot for real integrations; no production deployment is implied.
  • Document product setup and visible operating outcomes so another owner can configure the workflow without changing its shared logic.

Proposed approach — mentor analysis

This section explains a possible implementation; it is not an accepted design, a new requirement, or authorization to build.

As mentor analysis, prepare two contrasting profiles through the existing owner interface, use controlled integrations that capture product context, and drive both through feedback, proposal, approval, bounded work, review, and delivery. Include a rolling-fallback example and a stopped attempt, then demonstrate that cross-product identifiers and authority cannot affect the other product. Record visible outcomes and setup steps another owner can repeat.

The issue does not name pilot products, vendors, credentials, runner platform, or deployment environment. A real-integration pilot needs its documented authorization; these learning pages neither perform it nor grant that authority.

Concepts to learn

  • Reuse is demonstrated by varying configuration while keeping shared logic unchanged.
  • Isolation is an end-to-end property: a safe intake boundary alone cannot prove safe scheduling or billing.
  • Controlled integration proof and an authorized real pilot provide different kinds of evidence.

Alternatives and tradeoffs

Duplicating the workflow for a second product is quick but fails the shared-logic goal. A single full-lifecycle happy path misses cross-product authority and exceptional-state leaks. Running all proof against real vendors can be costly and nondeterministic; controlled adapters make failures repeatable, while the separate authorized pilot establishes actual integration behavior.

Failure scenarios

  • Product A’s approval is used to run product B’s ticket: deny cross-product authority.
  • A retry key or scheduled weekend identity lacks product context: attempts can collide or suppress each other.
  • Inventory or fulfilled evidence from one product changes the other’s demand: preserve product-scoped state.
  • A controlled adapter test is described as a real pilot: report the actual evidence boundary and pending authorization.

Test strategy

Run two product lifecycles with controlled clocks and tracker, runner, usage, validation, preview, and release integrations once preceding slices exist. Vary approvers, destinations, schedules, limits, and inventory; deliberately swap identifiers and approval references. Include rolling fallback, a stopped/reapproved attempt, delivery, and next evaluation. Assert no cross-product data, authority, usage, or scheduling effects. Document a separately authorized pilot and reproducible owner setup outcomes.
