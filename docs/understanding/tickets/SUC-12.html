SUC-12: Turn build output into a tested review package

Linear status: Backlog · Evidence date: 2026-10-09 · Local branch: feature/SUC-7-group-feedback · HEAD: b80de3d.

Requirements and status come from the live Linear evidence supplied by the main agent. Local behavior is based on repository inspection, not a fresh test run or proof of merge. Read the original SUC-12 issue; parent: SUC-5. Source user stories: 32, 33.

Problem and why it matters

A draft containing code changes is only the start of review. The reviewer needs configured check results, evidence for each acceptance criterion, a change summary, unresolved questions, and a preview when applicable. Missing or failed evidence must remain visible so a plausible summary cannot conceal an incomplete result.

Architecture connection

SUC-11 supplies the bounded attempt and preserved draft. SUC-12 interprets that output against the approved acceptance criteria and the product’s validation/preview instructions. The persistent profile from ADR 0001 carries those instructions across requests. A review package is evidence about work; SUC-15 still requires separate delivery confirmation.

Source acceptance criteria

The following criteria reproduce the supplied Linear wording. Checkbox completion is not inferred from the issue status.

  • Run the product's configured checks and report evidence for every acceptance criterion.
  • Keep the pull request in draft state when required checks fail or required acceptance evidence is missing; explicitly report unverifiable criteria.
  • Produce a preview where applicable using configured instructions and attach its reference to the review package.
  • Present unresolved questions and failures alongside completed work without implying deployment.
  • Verify successful and failed review packages at the same workflow boundary using controlled validation and preview integrations.

Proposed approach — mentor analysis

This section explains a possible implementation; it is not an accepted design, a new requirement, or authorization to build.

As mentor analysis, map each approved acceptance criterion to observable evidence and run configured checks through controlled adapters. Assemble results, change summary, questions, and an applicable preview reference around a particular attempt/draft revision. Explicitly record unverifiable criteria. Preserve draft state whenever required checks fail or required evidence is missing.

The ticket does not select an evidence format, preview provider, or rule for marking a successful draft ready for review. “Preview where applicable” needs a product-specific interpretation; it does not authorize deployment.

Concepts to learn

  • A passing command and acceptance-criterion evidence answer different questions.
  • An unverifiable criterion should be reported explicitly rather than guessed complete.
  • Review state belongs to a draft revision; delivery belongs to a separate release/confirmation boundary.

Alternatives and tradeoffs

A pass/fail summary is compact but hides which behavior was established. A criterion evidence matrix is more explicit and needs links that remain tied to the reviewed revision. A preview can reveal usability problems that tests miss, but it may be inapplicable or fail to start; the reporting design must preserve those outcomes without implying deployment.

Failure scenarios

  • All configured checks pass but one required criterion has no evidence: keep draft and report the gap.
  • A check fails after useful changes were made: preserve changes and show failure details.
  • A preview is applicable but unavailable: report that outcome with remaining questions.
  • A summary implies delivery merely because validation passed: keep release confirmation separate.

Test strategy

Use controlled validation and preview integrations at the same workflow boundary as the future runner. Verify successful packages, failed checks, missing acceptance evidence, explicitly unverifiable criteria, preview success/failure, and not-applicable preview behavior once defined. Assert draft retention for failed required checks or missing required evidence and inspect the completed-work/open-question report.

  2. Why should a review package identify the draft revision it describes?
  3. What must a failed package preserve for SUC-14?
