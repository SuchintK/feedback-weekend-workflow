SUC-13: Schedule the approved weekend build reliably

Linear status: Backlog · Evidence date: 2026-10-09 · Local branch: feature/SUC-7-group-feedback · HEAD: b80de3d.

Requirements and status come from the live Linear evidence supplied by the main agent. Local behavior is based on repository inspection, not a fresh test run or proof of merge. Read the original SUC-13 issue; parent: SUC-5. Source user stories: 28, 29, 31.

Problem and why it matters

A scheduler will encounter repeated events, restarts, late approval, and local-time boundaries. It must evaluate proposals on the configured schedule and start at most one small approved ticket for each product’s weekend. A missed deadline should produce a visible skip while retaining the unapproved proposal for reconsideration.

Architecture connection

This is a time-driven caller of the same guarded execution boundary supplied by SUC-11. It must preserve SUC-10’s version-bound approval and the product-scoped operating contract from ADR 0001. Reliable scheduling concerns durable decisions about attempts, not just a cron expression.

Source acceptance criteria

The following criteria reproduce the supplied Linear wording. Checkbox completion is not inferred from the issue status.

  • Use configured proposal time, approval deadline, build window, and timezone rather than hard-coded dates.
  • Retain unapproved proposals for reconsideration, but skip implementation if the deadline is missed.
  • Recheck approval and ticket version at execution; process only one small approved ticket per product per weekend.
  • Repeated scheduler events and restarts cannot start duplicate attempts; schedule reporting makes skipped or started work visible.
  • Verify the scheduled approval-to-build path with a controllable clock, including timezone boundaries, late approval, invalidated approval, and repeated events.

Proposed approach — mentor analysis

This section explains a possible implementation; it is not an accepted design, a new requirement, or authorization to build.

As mentor analysis, resolve product-local schedule boundaries using an injectable clock, evaluate feedback at proposal time, and later decide whether a current approved version can start before the deadline and inside the build window. Persist a product/weekend decision so repeated events reconcile with the same attempt. Reuse SUC-11’s checks at execution instead of trusting an earlier scheduler check.

Weekend definition, missed-event catch-up, daylight-saving ambiguities, exact deadline inclusivity, and coordination across scheduler instances remain unresolved. Do not equate repeated-event safety with a particular lock or queue implementation.

Concepts to learn

  • Local calendar boundaries differ from fixed UTC durations.
  • An at-most-one outcome requires durable reconciliation across repeated events and restarts.
  • Execution-time revalidation protects against approval changes after a scheduler decision.

Alternatives and tradeoffs

A cron job is a delivery mechanism but does not by itself prevent duplicates or resolve missed deadlines. A persisted decision ledger gives visibility and recovery at storage/coordination cost. Polling and queued events are both plausible mechanisms; neither is selected. The specified outcome matters more than assuming exactly-once event delivery.

Failure scenarios

  • Approval arrives after the configured deadline: retain the proposal but skip that implementation window.
  • Approval is invalidated after scheduling: execution recheck must deny the old version.
  • A scheduler restarts and receives the same event: do not start a second attempt.
  • Two products share a timezone but have different windows: each must use its own schedule and authority.

Test strategy

Drive the scheduled approval-to-build path using a controllable clock, controlled evaluator/runner, and durable state across reconstructed scheduler instances. Cover timezone/weekend boundaries, late approval, invalidated approval, out-of-window starts, and repeated events. Assert at most one small approved ticket per product/weekend and visible skip/start reasons. Boundary expectations depend on resolving the open calendar policy.

Explain it back

  1. Why is a cron expression insufficient to prove reliable scheduling?
  2. What must be rechecked after a ticket was approved and scheduled?
  3. What happens to a proposal that misses the approval deadline?
  4. Which identity prevents a repeated weekend event from starting twice?
