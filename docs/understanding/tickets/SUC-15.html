SUC-15: Confirm delivery and retire only satisfied demand

Linear status: Backlog · Evidence date: 2026-10-09 · Local branch: feature/SUC-7-group-feedback · HEAD: b80de3d.

Requirements and status come from the live Linear evidence supplied by the main agent. Local behavior is based on repository inspection, not a fresh test run or proof of merge. Read the original SUC-15 issue; parent: SUC-5. Source user stories: 18, 19, 20, 36, 37.

Problem and why it matters

Implementation progress is different from delivery. A draft PR, merge, or successful check may still leave customers without the requested behavior. Once delivery is verified, the workflow must retire only the evidence actually satisfied so partial fulfillment and new extensions remain visible in later demand calculations.

Architecture connection

This closes the loop between SUC-8 proposal evidence, SUC-12 review output, and the verified inventory/candidates established by ADR 0002. Original feedback remains durable evidence even when it stops contributing to demand. Inventory updates need coordination with the current verification snapshot rather than silently treating an old snapshot as current.

Source acceptance criteria

The following criteria reproduce the supplied Linear wording. Checkbox completion is not inferred from the issue status.

  • Require a verified configured release signal or explicit owner delivery confirmation; a pull request or merge alone does not fulfill demand.
  • Link delivered scope to the evidence it satisfies, retain original records, and exclude only that satisfied evidence from later demand calculations.
  • Update the inventory after delivery; retain unmet extensions and escalate ambiguous fulfillment matches with suggested interpretations.
  • Process repeated delivery signals idempotently and keep pending or unfinished builds from retiring demand.
  • Verify a full proposal-to-build-to-delivery-to-next-evaluation path, including partial fulfillment and new extension requests.

Current implementation versus planned work

Backlog and absent locally. Candidates can be marked fulfilled or unmet-extension during owner-reviewed analysis, but that does not implement verified delivery. There is no release-signal adapter, delivery confirmation, scope-to-evidence fulfillment ledger, or later demand evaluator. Existing profile fields also do not explicitly model a release-verification policy.

Proposed approach — mentor analysis

This section explains a possible implementation; it is not an accepted design, a new requirement, or authorization to build.

As mentor analysis, verify the configured release signal or authenticated owner confirmation, identify delivered scope, and match that scope to particular evidence. Persist a delivery/fulfillment record while retaining originals. Exclude only satisfied evidence from future counts, update inventory, and surface ambiguous matches with interpretations instead of assuming all linked requests are fulfilled.

Release identity/authentication, partial fulfillment within a single feedback record, inventory reverification, and a durable delivery-idempotency identity need design. A PR identifier may connect review evidence, but cannot be the delivery proof by itself.

Durable state and readiness

Proposed backlog state: verified delivery evidence, delivered scope, matched feedback/candidate links, satisfied versus remaining scope, signal idempotency identity, and resulting inventory change. A fulfillment ledger is a proposed representation, not an accepted schema. Original feedback must remain available.

Readiness: delivery does not grant execution authority or automatically change current readiness flags. Updating inventory can make SUC-7’s old verification snapshot stale; how delivery verification establishes a current inventory record remains an open contract. Demand eligibility changes only for satisfied evidence.

Concepts to learn

  • Delivery evidence and review evidence prove different events.
  • Retiring a record from demand does not require deleting its history.
  • Partial fulfillment requires scope-sensitive matching rather than a blanket delivered flag on a broad candidate.

Alternatives and tradeoffs

Marking a whole ticket fulfilled is simple but can erase unmet extensions. Deleting feedback loses provenance and prevents auditing. Scope-to-evidence links preserve nuance but introduce ambiguity when a single message requests several behaviors. Owner confirmation is an explicit supported path; automated release verification needs a configured trust policy.

Failure scenarios

  • A PR merges but no verified delivery is recorded: keep demand eligible.
  • Only one requested export format is delivered: retain the unmet extension.
  • A release webhook repeats: process the same delivery without retiring additional evidence.
  • A delivery match is ambiguous: present questions and suggested interpretations rather than guessing fulfillment.

Test strategy

Exercise proposal → build/review → verified delivery → next evaluation with controlled tracker, runner, release, and clock integrations. Cover owner confirmation, rejected/unverified signal, repeated delivery, pending builds, partial fulfillment, and later extension feedback. Assert original records remain, inventory changes are visible, and only satisfied eligible evidence stops contributing to counts. Snapshot freshness behavior needs an explicit decision.

Explain it back

  1. Why are a merged PR and a successful review package insufficient to retire demand?
  2. How can a broad request be partly satisfied while preserving its remaining demand?
  3. Which identity makes repeated delivery signals idempotent?
  4. What happens to SUC-7 verification when delivery updates inventory?
