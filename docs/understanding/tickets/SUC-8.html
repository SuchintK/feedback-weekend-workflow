SUC-8: Propose one feature from current-week demand

Linear status: Backlog · Evidence date: 2026-10-09 · Local branch: feature/SUC-7-group-feedback · HEAD: b80de3d.

Requirements and status come from the live Linear evidence supplied by the main agent. Local behavior is based on repository inspection, not a fresh test run or proof of merge. Read the original SUC-8 issue; parent: SUC-5. Source user stories: 10, 11, 13, 14, 21, 22, 23, 25.

Problem and why it matters

A weekly proposal should represent distinct customers asking for eligible unmet scope. Message volume alone is misleading: repeated requests from one customer must not outweigh several customers, and bugs or satisfied requests must not become new feature proposals. The owner needs one explainable selection and visible alternatives.

Architecture connection

This is the first demand-selection consumer of ADR 0002. It builds on durable candidates and original evidence, applying eligibility and time filtering before counting customers. Proposal publication introduces an external side effect whose retry behavior must preserve the one-proposal outcome.

Source acceptance criteria

The following criteria reproduce the supplied Linear wording. Checkbox completion is not inferred from the issue status.

  • Use the product timezone and configurable threshold, defaulting to three distinct customers per feature.
  • Count each customer once per candidate from eligible underlying evidence and explain the count.
  • Rank by customer count, goal alignment, then smaller scope; show alternatives and support an owner override.
  • Create or update one proposal containing scope, acceptance criteria, exclusions, supporting feedback, and assumptions; prevent duplicate tickets on repeated evaluation.
  • When nothing qualifies, report that outcome without starting a build; verify scoring, ranking, publication, and skip behavior with controlled external integrations.

Proposed approach — mentor analysis

This section explains a possible implementation; it is not an accepted design, a new requirement, or authorization to build.

As mentor analysis, separate a side-effect-free evaluation result from publication. Resolve the product’s current-week interval, filter eligible evidence, compute a set of customer IDs for each candidate, then apply count, goal alignment, and smaller scope in that order. Return counts and alternatives so the owner can explain or override selection. Publish the selected proposal using a stable persisted publication identity to reconcile retries. The exact identity and recovery protocol need design.

Week boundaries, residual ties, goal-alignment scoring, scope estimates, and override restrictions remain undecided. A default of three is specified; a particular field name or scoring formula is not.

Concepts to learn

  • Distinct-customer counting uses sets over eligible records rather than message totals.
  • A lexicographic ranking applies priorities in order; a weighted score could produce a different policy.
  • Publication retries need reconciliation because a remote create can succeed before its response is received.

Alternatives and tradeoffs

A weighted score makes tuning easy but can violate the specified customer-count-first ordering. A pure evaluator is easier to inspect and replay than evaluation mixed with remote writes. Creating a new ticket on every evaluation is simple but violates duplicate prevention. Persisted references and tracker lookup can help, with unresolved failure-recovery tradeoffs.

Failure scenarios

  • One customer submits five messages: count that customer once for the candidate.
  • A fulfilled, bug, uncertain, or checked-ticket candidate has many requests: exclude it under ADR 0002.
  • A tracker create succeeds but the response is lost: reconcile before retrying creation.
  • No candidate qualifies: report the result without starting a runner; SUC-9 may later evaluate fallback.

Test strategy

Use a controllable clock and product timezone for date boundaries; include repeated customers, multiple candidates, and every eligibility disposition. Assert ranking order, explanations, alternative visibility, and an owner override once its semantics are settled. A controlled tracker should simulate create/update and an ambiguous failure after remote success. Assert repeated evaluation creates no duplicate and no-demand outcomes perform no build work.
