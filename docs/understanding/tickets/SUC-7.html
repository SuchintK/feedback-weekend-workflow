SUC-7: Group requests and filter existing functionality

Linear status: In Progress · Evidence date: 2026-10-09 · Local branch: feature/SUC-7-group-feedback · HEAD: b80de3d.

Requirements and status come from the live Linear evidence supplied by the main agent. Local behavior is based on repository inspection, not a fresh test run or proof of merge. Read the original SUC-7 issue; parent: SUC-5. Source user stories: 8, 9, 16, 17, 19, 20, 38.

Problem and why it matters

Several messages can describe one need, while similar wording can refer to different needs. Counting raw messages inflates demand, and proposing already delivered functionality or an existing ticket wastes work. The owner needs traceable candidates, explicit bugs, and a way to resolve uncertain scope.

Architecture connection

ADR 0002 chooses persisted candidates and an authenticated owner’s inventory snapshot so demand evaluation can reuse both candidates and evidence. Verification must match current repository/documentation references and inventory. A server-side ticket finder supplies ticket matches; customer text and analysis requests cannot assert operational authority.

Source acceptance criteria

The following criteria reproduce the supplied Linear wording. Checkbox completion is not inferred from the issue status.

  • Group differently worded requests by underlying need and preserve their original evidence; distinguish bugs from feature requests.
  • Let the owner verify an initial inventory grounded in product documentation and repository evidence.
  • Check candidates against existing functionality and tickets; reuse existing candidates rather than create duplicates.
  • Distinguish fulfilled scope from unmet extensions and present uncertain matches with clarification questions and suggested interpretations.
  • Customer feedback cannot change configuration, permissions, or authorize operations; verify this at the workflow boundary.

Dependencies and successor obligations

Direct blockers: SUC-6. Direct successors blocked by this ticket: SUC-8.

SUC-6 supplies the owner-scoped profile, repository/documentation context, goals, inventory, and feedback. SUC-8 may consume only feature candidates marked unmet or unmet extension that have no checked existing ticket. Bugs, fulfilled scope, and uncertain matches are excluded. Candidate reuse must preserve linked evidence so later customer counts can be recomputed.

Proposed approach — mentor analysis

This section explains a possible implementation; it is not an accepted design, a new requirement, or authorization to build.

Trace verification before analysis, then follow two differently worded feedback records into one underlying need. Inspect how a stable key and the underlying-need string enable reuse. A future autonomous grouping adapter could propose interpretations for review, but that is an alternative rather than an implemented or approved module. Keep real ticket discovery behind the server-side seam and distinguish “checked with no match” from an integration that was never wired.

Expected files and existing seams

src/workflow.ts contains candidate types, inventory snapshots, comparison validation, and persistence. src/server.ts parses owner-submitted analysis and injects the finder. src/start.ts exposes the current wiring gap. test/server.test.ts includes grouping, ticket reuse, and uncertain-fulfillment examples.

These are existing repository paths to inspect or potentially extend. Future module names and a final file split have not been approved.

ProductProfile inputs

Consumes goals, repository identity and documentationReferences, and inventory. Product ownership scopes access. A real ticket finder may need ticketDestination and configured integration references; its production wiring is not defined locally. Analysis does not require the complete build configuration.

Durable state and readiness

Implemented durable state: inventory snapshots capture product/owner, repository URL, documentation references, and inventory items. Candidates retain product, key, underlying need, kind, feedback IDs, and comparison outcome, optionally with a checked ticket or clarification details. Original feedback remains separate and is joined into response evidence.

Readiness: analysis requires analysis-ready configuration plus a current owner verification snapshot. Running analysis does not change readiness or grant build authority. Inventory/reference changes make the old snapshot insufficient until verification is repeated. Candidate eligibility for SUC-8 is distinct from product readiness.

Concepts to learn

  • Grouping is a semantic interpretation; preserving original evidence lets an owner audit that interpretation.
  • Inventory freshness and candidate eligibility are different checks.
  • A server-controlled integration result has a different trust boundary from customer text or request-supplied ticket claims.

Alternatives and tradeoffs

Transient analysis is simple but forces later evaluations to reconstruct identity and evidence, which ADR 0002 rejects. Explicit owner interpretation provides a controlled starting point but requires manual work. Automated grouping could reduce that work while introducing ambiguity, evaluation cost, and review decisions. Exact underlying-need strings are a current reuse mechanism, not proof of semantic equivalence across arbitrary wording.

Failure scenarios

  • An inventory snapshot predates a profile evidence change: reject analysis until current evidence is verified.
  • An uncertain comparison omits a question or suggested interpretations: reject the incomplete comparison.
  • A candidate reuses a key for another need or mixes another product’s feedback: reject conflicting or unauthorized evidence.
  • The startup finder is unwired: do not describe its no-match default as a verified real tracker search.

Test strategy

Use existing HTTP tests to inspect original evidence preservation, feature/bug separation, repeated-candidate reuse, verified inventory requirements, and clarification output. Inject a controlled finder for match and no-match cases. Ensure malicious feedback cannot update profile settings or authorize operations. These tests document the seam; real tracker wiring and autonomous interpretation remain separate gaps.
