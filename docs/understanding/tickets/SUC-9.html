SUC-9: Accumulate demand only when the current week is quiet

Linear status: Backlog · Evidence date: 2026-10-09 · Local branch: feature/SUC-7-group-feedback · HEAD: b80de3d.

Requirements and status come from the live Linear evidence supplied by the main agent. Local behavior is based on repository inspection, not a fresh test run or proof of merge. Read the original SUC-9 issue; parent: SUC-5. Source user stories: 12, 13, 14, 15.

Problem and why it matters

A useful feature may gather demand slowly across several weeks. Fallback makes that demand visible while preserving current-week precedence. The trigger depends on whether any current-week candidate crosses the demand threshold, regardless of whether its proposal has been approved.

Three weekly counts cannot simply be added: one customer can appear in every week. The rolling calculation must return to eligible original records and count unique customers across the whole window.

Architecture connection

This extends the SUC-8 evaluation policy without changing ADR 0002 candidate eligibility. Original feedback and stable customer identity make cross-week recalculation possible. Publication, ranking, and duplicate prevention must remain the same workflow behavior as current-week selection.

Source acceptance criteria

The following criteria reproduce the supplied Linear wording. Checkbox completion is not inferred from the issue status.

  • Trigger fallback only when no current-week candidate crosses the threshold, regardless of ticket approval state.
  • Default to the current week plus the preceding three weeks; make the window configurable.
  • Recalculate distinct customers across underlying eligible records instead of adding weekly totals; exclude evidence outside the window.
  • Use the same proposal, ranking, and duplicate-prevention behavior as current-week selection.
  • Verify current-week precedence, boundary dates, repeated customers across weeks, overlapping evaluations, and no-demand outcomes using a controllable clock.

Proposed approach — mentor analysis

This section explains a possible implementation; it is not an accepted design, a new requirement, or authorization to build.

As mentor analysis, first evaluate the current week using SUC-8’s eligibility and threshold policy. Only a result with no qualifying candidate should enter fallback. Compute a product-local interval for the configured number of weeks, read original eligible records, build customer-ID sets per candidate, and invoke the same ranking and publication path. Return an explanation that identifies the interval and distinct customers.

The default contains four weeks total, including the current one. Week start, endpoint inclusivity, daylight-saving behavior, valid configuration bounds, and handling of changes between repeated evaluations require decisions. Do not invent a new profile field name as an accepted contract.

Concepts to learn

  • Set union across original evidence avoids counting the same customer once per week.
  • Precedence is an explicit policy branch, not a preference added to a score.
  • A replayable interval explanation lets an owner understand why a candidate qualified.

Alternatives and tradeoffs

Adding weekly totals is cheap but overcounts customers who repeat themselves. Always evaluating the rolling window could hide current-week precedence and violates the fallback trigger. Reusing SUC-8’s publication behavior reduces divergence, while caching results would need freshness and overlapping-window rules that are not specified.

Failure scenarios

  • A current-week candidate qualifies but remains unapproved: fallback must stay off.
  • The same customer appears in three weeks: count once over the rolling window.
  • A record lies just outside the configured window: exclude it even if an earlier evaluation counted it.
  • Overlapping evaluations select the same candidate: preserve shared duplicate prevention rather than creating another proposal.

Test strategy

With a controllable clock, construct records at both interval boundaries and across timezone changes. Compare repeated customers across weeks against distinct customers. Assert a qualifying current-week candidate suppresses fallback regardless of approval, the default covers current plus three preceding weeks, and configuration changes the interval. Repeated/overlapping runs must reuse publication behavior and visibly report no-demand outcomes.
