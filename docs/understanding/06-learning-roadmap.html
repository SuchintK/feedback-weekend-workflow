Learning roadmap

Learn the running feedback service first, then the workflow it is intended to support. Every checkpoint below is a prompt for the learner to explain in their own words; no checkpoint has been marked understood.

Evidence baseline: 2026-10-09, HEAD b80de3d, branch feature/SUC-7-group-feedback. During discovery, npm test passed all seven tests and npm run typecheck passed. PR merge and deployment have not been verified.

Use the glossary for vocabulary and the learning unknowns to record questions without treating them as software defects.

Start in dependency order

Live issue status was verified during discovery: SUC-6 is Done; SUC-7 is In Progress; SUC-8 through SUC-16 are Backlog. The native dependencies match published-tickets.md. Status describes issue tracking, not a deployment guarantee.

  1. First: SUC-6 → SUC-7. Understand ownership, product configuration, feedback evidence, verification, and candidate analysis in the current source.
  2. Next: SUC-8 → SUC-9. Study intended current-week demand evaluation and rolling fallback after candidate semantics are clear.
  3. Then: SUC-8 → SUC-10 → SUC-11. Learn version-bound approval before bounded execution.
  4. After execution: SUC-11 → SUC-12 → SUC-14; SUC-11 also enables SUC-13. Review packages precede continuation; scheduling is a separate branch.
  5. Delivery and reuse: SUC-8 plus SUC-12 → SUC-15. Finally, SUC-16 depends on SUC-9, SUC-13, SUC-14, and SUC-15 to demonstrate the full workflow for a second product.

The dependency order is a study sequence, not evidence that later capabilities exist. See ticket dependencies for the full map.

Stepwise explain-back lesson plan

For each lesson: read the linked source, draw or narrate the path, answer the prompt without looking, then compare the explanation with the source. Record uncertainty in learning unknowns. Reading a page or passing a command does not establish understanding.

  1. Lesson 1 — actors and evidence: use domain terms and Product/Feedback. Explain who submits feedback through this service, who the customer ID identifies, and which actor can inspect it. Checkpoint: pending.
  2. Lesson 2 — one request end to end: trace POST /products from startup through authentication and parsing to registerProduct and write. Explain the response and persisted fields. Checkpoint: pending.
  3. Lesson 3 — partial to analysis-ready: trace mergeProfile and readiness predicates. Explain why an incomplete repository can be saved and why a positive readiness flag does not satisfy the inventory-verification gate. Checkpoint: pending.
  4. Lesson 4 — verified analysis: trace verification and analysis with two differently worded messages. Explain which grouping decisions the owner supplies, what exact-string reuse means, and what an uncertain match must contain. Checkpoint: pending.
  5. Lesson 5 — storage and failure: inspect read, write, and the server catch block. Explain missing versus malformed storage, an invalid ticket response, and a finder that throws. Distinguish a code path from an observed failure. Checkpoint: pending.
  6. Lesson 6 — tests as evidence: read all seven tests. Pair each claim with an assertion; identify one restart scenario and one cross-product scenario that are not covered. The seven-pass result is a baseline, not a learner assessment. Checkpoint: pending.
  7. Lesson 7 — intended lifecycle: follow SUC-8 through SUC-16. Explain how feedback could eventually lead to a proposal, approved attempt, review package, and delivery, explicitly marking every unimplemented step. Checkpoint: pending.
